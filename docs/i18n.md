# Frontend i18n (Lingui)

`apps/web` is translated with [Lingui](https://lingui.dev) 6. Source strings are written in
Chinese; the message id is the zh-CN text, so an untranslated message falls back to Chinese.
Languages: `zh-CN` (source) and `en`, listed in `apps/web/lingui.config.ts` and
`apps/web/app/lib/locale.ts`.

## Writing strings

```tsx
import { Trans, useLingui } from '@lingui/react/macro'

const { t } = useLingui()
<button aria-label={t`关闭`}><Trans>返回首页</Trans></button>
t({ message: '回复', context: 'button' }) // `context` tells apart same-looking messages
```

- Use named locals in placeholders (`const label = theme.label; t\`${label}\``), not member
  expressions, or the placeholder becomes `{0}`. A value may be interpolated and then pluralised
  in the English translation only: write `{count} 主题`in the source and`{count, plural, one {# thread} other {# threads}}`in`en.po`.
- Never glue words: `返回${label}` or `取消${label}` cannot be translated. Make the whole phrase one
  message, or pass two separate messages.
- Ambiguous words carry a `context` (`主题` = colour theme / thread; `回复` = verb / noun /
  "replying to"; `关注` = verb / count / home tab). Reuse an existing context when the meaning is
  the same.
- Module-level constants cannot call `t` at load time: define them with `msg` from
  `@lingui/core/macro` and translate at render with `i18n._(label)` (tabs, role names, report
  reasons, toolbar tools).
- Code without hooks takes an `I18n` and uses `t(i18n)\`...\``: formatting helpers, fetch helpers,
  Tiptap extensions (they receive it through `composer.editor`). In a loader or action use
  `await i18nFromRequest(request)` (`lib/i18n.server.ts`); in `meta()`use`i18nOfRoot(matches[0].loaderData)`.
- Do not translate user content, site configuration (name, tagline, footer groups) or API text;
  see "Not translated yet".

## Workflow

```sh
pnpm --dir apps/web i18n:extract   # update app/locales/*.po from the source
# fill the empty msgstr in app/locales/en.po
pnpm --dir apps/web i18n:check     # extract --clean, then compile --strict (fails on missing en)
```

`.po` files are committed. The Lingui Vite plugin compiles them on import; there is no separate
compile step for the app (`i18n:check` writes `app/locales/*.js` as a by-product; they are ignored).

## How a request is served

- `localeFromRequest` (`app/lib/locale.ts`): `forum_locale` cookie, else `Accept-Language`, else zh-CN.
- The root loader returns `locale` and the compiled `messages`; `Layout` builds a **per-render**
  `I18n` (`createI18n`) and wraps `children` in `I18nProvider`. Never use the global `i18n`
  singleton on the server: concurrent requests would leak languages.
- Production builds strip the source text from `t`/`<Trans>`, so a render without a catalog would
  show raw message ids. `createI18n` therefore defaults to the bundled zh-CN catalog, and a
  catch-all route (`routes/not-found.tsx`) makes the root loader run for unknown URLs too.
- Switching language (`LocaleSwitcher`) writes the cookie and revalidates the root loader.

## Adding a language

Add it to `locales` in `lingui.config.ts`, to `LOCALES` and `isLocaleId`/`fromAcceptLanguage` in
`app/lib/locale.ts`, and to `CATALOGS` in `app/lib/i18n.server.ts` (a type error until you do).

## API errors

An API error is data: `{ code, message, key, params }`. `key` and `params` come from
`packages/domain/src/errors.ts` (`errorDetail`, `failure`), where each key also has its Chinese
fallback `message` for clients that do not know the key. To add one:

1. Add the key and its params type to `ErrorSpecs`, and its Chinese text to `ERROR_TEXT`.
2. Produce it in the plugin with `failure('invalid', 'my.key', { ...params })` (or a validator's
   `error`, or a hook's `key`/`params`).
3. Word it in `apps/web/app/lib/api-errors.ts` and translate it in `en.po`.

`tests/api-errors.test.ts` fails if the web app's Chinese differs from the API's fallback or a
key is missing. `forum-api.server.ts` words every failed call in the visitor's language, so loaders
and actions keep reading `result.error.message`; code that calls the API from the browser uses
`apiErrorTextOfBody`.

## Notifications and stand-in users

A notification stores its title as a key and params (`NoticeSpecs` in `packages/domain/src/notices.ts`)
beside the finished Chinese `title`; the web app words it in `apps/web/app/lib/notices.ts`. Rows
written before the key columns existed were filled in by the `0001_notice_keys` migration, and
a title no pattern matched keeps its Chinese text.

A user the backend cannot look up is `placeholderUser(id, kind)`: the Chinese name plus
`ext.placeholder`, which the web app swaps for a translated name. Add a notice key the same way as an
error key: spec and Chinese text in the domain, word it in `notices.ts`, translate it in `en.po`;
`tests/notices.test.ts` checks the Chinese matches. `forum-api.server.ts` applies both to every API
response, so components read `title` and `displayName` as before.

## Not translated yet

The mail plugin writes email subjects and bodies in Chinese, and the Workbench (admin) screens are
Chinese only.
